# Technique: Patching / Defense (KotH)

**Навіщо:** на основному етапі треба не лише атакувати, а й **патчити** свою машину: закрити вразливість, якою зайшов, щоб суперники в групі не пройшли тим самим шляхом. Правило — патчити **в міру**: сервіс має лишатися живим.
← [MASTER](../01-roadmaps/MASTER-ROADMAP.md) · [initial-access](../01-roadmaps/initial-access.md)

> Правила (SG main): не вимикати машину, не видаляти сервіси/системні файли, **не видаляти й не змінювати прапорці**, не блокувати інших фаєрволом. Моніторинг стану машини високий — за деструктив бан. Патч має лишити сервіс робочим.

---

## Принцип
1. Зайшов через вразливість → **зафіксуй шлях** (щоб відновити, якщо щось зламається, і щоб пояснити організаторам).
2. Закрий саме цю діру, **не ламаючи функціонал** сервісу.
3. Перевір, що сервіс досі відповідає (той самий запит → вже без експлуатації).

## Готові патчі за типом вразливості
| Вектор входу | Як закрити (не вбиваючи сервіс) |
|---|---|
| **Веб-шелл** (залитий файл) | видалити лише залитий шелл: `rm /var/www/html/s.php`; знайти інші: `grep -rlE 'system\(|passthru\(|eval\(' /var/www 2>/dev/null` |
| **Upload без перевірки** | у коді додати перевірку розширення/типу; або прибрати право запису: `chmod -R a-w /var/www/html/uploads` (якщо аплоуд не критичний) |
| **LFI / traversal** | у параметрі прибрати `../` (basename) або whitelист; тимчасово — закрити доступ до логів: `chmod 640 /var/log/apache2/access.log` |
| **SQLi** | складно патчити код нашвидкуруч → мінімум: прибрати креди БД із відповіді, обмежити права БД-юзера (`REVOKE FILE`), прибрати `secure_file_priv` write |
| **Command injection** | у коді екранувати/прибрати shell-виклик; якщо не можна — обмежити вхід whitelист-ом символів |
| **Дефолтні/слабкі креди** | змінити пароль сервісу на свій: `passwd <user>`, оновити конфіг додатка/БД/SSH |
| **Відкритий Redis/БД** | поставити пароль (`CONFIG SET requirepass ...` / `ALTER USER`), прив'язати до `127.0.0.1` |
| **SUID/кривий cron** | забрати зайвий SUID: `chmod u-s /path/bin`; виправити права на writable cron-скрипт: `chmod 700 /path/script.sh` (якщо не зламає сервіс) |
| **Знайдений приватний ключ** | прибрати ключ з `authorized_keys`, якщо він лишній |

## Після root — утримання вершини
```bash
echo '<НАЗВА_КОМАНДИ>' > /king.txt          # вписати свою команду (уточнити шлях платформи)
# змінити паролі root/адмін-юзерів на свої, щоб суперники не зайшли тим же шляхом:
passwd root
# закрити вектор, яким піднявся до root (SUID/cron/креди) — див. таблицю вище
```

## Чого НЕ робити (бан)
- Не видаляти/міняти прапорці й системні файли.
- Не вимикати сервіси й машину.
- Не блокувати інших фаєрволом, не атакувати чужі IP (навіть із захопленої машини).
- Патч, що «вбиває» сервіс (сервіс не відповідає) — гірше за відсутність патчу: може зняти бали й викликати питання організаторів.

## Пастки
- Перед патчем переконайся, що розумієш, що саме закриваєш — інакше зламаєш робочий функціонал.
- Тримай нотатку «вектор → як зайшов → як пропатчив» для пояснення організаторам.
